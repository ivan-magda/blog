2. Historical cross-module optimization A/B experiment

Release LockBench; target 3 seconds per invocation; 10,000 emits between outer
clock checks; debounce interval 3,600 seconds. One listed run per configuration.
The interval keeps callback delivery outside the repeated-emit workload.

Command structure, retaining actual arguments and execution order while
omitting output filtering and cosmetic shell printing:

  for mode in 0 1; do
      CMO=$mode swift build -c release --product LockBench
      .build/release/LockBench profile 3 fast
      .build/release/LockBench profile 3
  done

Saved output:
  CMO=0  fast: emits: 27580000
  CMO=0  article: emits: 15770000
  CMO=1  fast: emits: 257900000
  CMO=1  article: emits: 15680000

CMO toggled the historical Debounce target's -cross-module-optimization flag.
These counts compare throughput over a target time window. They are neither
medians nor directly measured per-call latencies. The clock was checked in
batches, so an invocation could run slightly beyond its target window.

The old profile banner still used the OptimizedDebounce name in fast mode;
the saved harness selection code and FastDebounce sample symbols identify
the actual prototype. The current package is not the original historical
FastDebounce implementation and its current manifest does not expose this
old CMO environment toggle as a reproduction interface.
